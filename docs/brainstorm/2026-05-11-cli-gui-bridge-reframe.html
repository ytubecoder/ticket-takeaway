The reframe: a shared steering protocol

Not "how do bits flow from CLI to TT" — that's plumbing. The real question is: what primitives let GUI-semi-automation and CLI-direct-steering cooperate around the same work?

TWO FIRST-CLASS SURFACES — same primitives
GUI — TT dashboard
  • Semi-automation (workflows, kitchen)
  • Multi-project portfolio view
  • Triage, observe, intervene
  • The rhizome made visible (parent ↔ children)
⇔
bidirectional
CLI/TUI — your coding session
  • Direct steering, vibe coding
  • Linear, warm, cached context
  • Where ideas surface in flight
  • You + model in a tight loop
↓ both speak ↓
THE STEERING PROTOCOL
propose(items, parent?)
Candidate tickets — land in a triage tray, not committed yet
fork(fragment, parent)
Spawn an agent on a sub-task with packaged context. Returns child ticket id.
stream(filter?)
Subscribe to live activity — child output, status changes, completions
reabsorb(child)
Fold result back into parent summary — new jump-off points appear
jump(ticket, characteristic)
From a feature summary, fork on a specific characteristic. The Surface-A flow.
list, get, link, accept, …
Everything you can already do in the GUI, callable from anywhere
CLIENT 1 — MCP server for the agent
Your Claude/Codex session has these primitives as tools. The model itself can say "I'll fork the W,X,Y,Z items as sub-tickets — confirm?" and call fork four times. No PTY proxying. No clipboard. The agent is the first-class participant.
CLIENT 2 — tt CLI for you
tt fork <parent> "fragment", tt propose < bullets.txt, tt stream in a side tmux pane. You can drop into manual mode whenever your model isn't doing what you want.

If this lands, the deliverable is: a small set of protocol primitives + two thin clients (MCP + tt CLI), both backed by the existing TT API. The GUI doesn't change much — it already shows everything that flows through.
